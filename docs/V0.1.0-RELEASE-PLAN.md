# lnwjud Watcher v0.1.0 — Release Completion Plan

Status: **v0.1.0 RELEASE CHECKLIST**
Source branch: **dev**  
Release branch: **main**  
Release target: **v0.1.0**  
Product boundary: **read-only monitoring only**

This document is the authoritative implementation checklist for the first public lnwjud Watcher release. Do not tag or publish v0.1.0 until every release gate in this document is satisfied with evidence.

## Product goal

lnwjud Watcher must be usable by normal users, not only developers. A user should be able to install/open Watcher, choose a language, connect to a lnwjud runtime with a guided zero/one-click path where possible, and see live agent/goal/activity state on Web/PWA, Android, and iOS without manually refreshing.

The product must retain the LNWJUD family identity while having a distinct Watcher visual language built around observability, live status, and the approved eye/radar logo.

## Non-negotiable boundaries

- lnwjud runtime is the source of truth.
- Watcher never reads lnwjud databases or internal files directly.
- Watcher Protocol v1 remains read-only.
- No shell execution, MCP mutation, filesystem mutation, arbitrary commands, pause/resume, approval, or hidden model reasoning in v0.1.0.
- Remote payloads are untrusted and validated at runtime.
- Remote endpoints use HTTPS/WSS; cleartext is loopback-only.
- Secrets/tokens must not be exposed in URLs, logs, screenshots, README examples, or persistent browser storage.
- Work lands on `dev`, then PR to `main`; only the verified merge SHA may be tagged.

## Phase 1 — Brand assets and design system

### Assets

Canonical files:

- `public/brand/lnwjud-watcher-logo-dark.png` — approved dark-background hero/logo.
- `public/brand/lnwjud-watcher-logo-transparent.png` — approved transparent PNG.
- Derive app/PWA icons and splash assets from the approved transparent master without changing the logo concept.
- Use simple ASCII filenames only.

### Visual system

Create a custom Watcher system that belongs to LNWJUD but is not a clone of the reference dashboard:

- near-black / deep navy foundations;
- metallic gold / amber monitoring accents;
- warm white foreground;
- restrained live-status colors;
- eye/radar/orbit motifs only as small brand accents;
- clear state hierarchy over decorative effects;
- accessible contrast and reduced-motion support;
- desktop and mobile compositions designed independently from the same tokens.

### Typography

Self-host **Prompt** for Thai + Latin across Web/PWA and native shells.

Required:
- bundle local WOFF2 font assets in the repository/application;
- no runtime Google Fonts dependency;
- define stable weight mapping;
- use system fallback only when local font fails.

## Phase 2 — Thai / English product localization

Implement complete locale infrastructure before translating individual screens.

Required locales:

- `th` — Thai
- `en` — English

Required behavior:

- first run defaults from device/browser locale;
- explicit TH/EN switch in onboarding/settings;
- locale persists locally;
- all navigation, states, empty states, onboarding, settings, errors, connection guidance, relative time, date/time, provider instructions, accessibility labels and CTA copy are localized;
- no mixed-language UI in either locale;
- protocol/domain values stay language-neutral and are mapped at presentation time.

## Phase 3 — Realtime-first freshness

Primary path:

1. initial `GET /api/v1/snapshot`;
2. open `WS /api/v1/events`;
3. apply validated events immediately;
4. after reconnect, refresh the authoritative snapshot;
5. surface connection state and last authoritative update time.

Fallback:

- when realtime is degraded/disconnected, automatically request a snapshot every **5 seconds** while the app is visible;
- stop fallback polling as soon as the WebSocket is healthy;
- avoid overlapping requests;
- manual refresh remains available;
- refresh on app/tab resume when stale;
- implement bounded reconnect backoff + jitter;
- avoid UI flicker or duplicate timeline events.

Do not expose hidden chain-of-thought. Analyzing/thinking states are only observable summarized activity emitted by lnwjud.

## Phase 4 — lnwjud runtime Watcher API

This release is not complete with demo data alone. The paired `E:\lnwjud` runtime must implement Watcher Protocol v1.

Required server surface:

- `GET /api/v1/snapshot`
- `WS /api/v1/events`
- read-only authentication suitable for tunnel exposure;
- stable instance id/name/platform/version;
- runtime health;
- current durable goal + evidence-based milestone progress;
- active observable agents/workers;
- sanitized activity/event timeline;
- sanitized Git baseline/status where available;
- server time / freshness fields;
- redaction before data leaves the runtime.

Event sources should use structured runtime events. Do not scrape human log text as the primary protocol.

Cross-repo contract validation must prove the lnwjud response/event schemas match the Watcher client.

## Phase 5 — Consumer onboarding

First run must answer four questions without requiring terminal knowledge:

1. What is lnwjud Watcher?
2. Where is my lnwjud runtime?
3. How do I expose it securely?
4. How do I know the connection works?

Happy path:

- choose TH/EN;
- choose **This device / Local**, **zrok**, **Cloudflare**, **Tailscale**, **ngrok**, or **Custom HTTPS**;
- show the shortest provider-specific setup;
- accept/paste a generated endpoint or scan/pair when supported;
- run connection test;
- enter the live Overview.

No user should need to edit JSON/config files for ordinary setup.

## Phase 6 — Remote access providers

Provider abstraction must not change Watcher Protocol semantics.

### Local / LAN

- loopback happy path on the same machine;
- LAN guidance only when the user understands network exposure;
- warn before insecure non-loopback HTTP.

### zrok

Target: easiest free public option for many users.

Provide:

- Windows install/setup script where safe;
- macOS install/setup script where safe;
- Linux install/setup script where safe;
- detection of existing zrok installation;
- clear steps for account/environment enablement when provider authorization cannot be automated;
- command generation/copy buttons;
- how to stop/revoke the share;
- troubleshooting for URL/auth/reconnect.

### Cloudflare Tunnel

Provide:

- guided Quick Tunnel only as a temporary/testing option;
- production guidance for authenticated Cloudflare Tunnel/Access;
- installer/detection helpers where feasible;
- clear ownership separation: Watcher does not ask for unnecessary Cloudflare secrets.

### Tailscale

Cover both:

- Tailscale Serve — private/tailnet-only;
- Tailscale Funnel — public HTTPS.

Provide platform install links/guidance and detection/helper commands where feasible. Explain the security difference clearly.

### ngrok

- reuse existing ngrok users cleanly;
- installer/detection/helper where feasible;
- avoid storing auth tokens in Watcher.

### Custom HTTPS

- support user-provided reverse proxy/domain;
- validate HTTPS URL;
- document CORS/WebSocket/TLS requirements;
- give examples without making one reverse proxy mandatory.

## Phase 10 — Release workflow

Release only from clean verified state.

1. Finish implementation on `dev`.
2. Review working tree and cross-file impact.
3. Run local quality gates.
4. Push `dev`.
5. Open/update PR `dev -> main`.
6. Watch the exact required GitHub Actions run IDs to terminal success.
7. Merge only after all required jobs are green.
8. Re-run/verify CI on the merged `main` SHA.
9. Tag the verified merge SHA as `v0.1.0`.
10. Watch the exact release workflow to terminal success.
11. Verify GitHub Release exists and assets open:
    - Web/PWA bundle;
    - Android artifact;
    - iOS evaluation artifact;
    - release notes.
12. Verify README badges/download links resolve to v0.1.0.
13. Mark durable acceptance criteria complete and close the continuation watchdog only after release evidence is verified.

## Release-definition checklist

v0.1.0 is **not complete** until all are true:

- [ ] approved logo filenames/locations are canonical;
- [ ] self-hosted Prompt works offline;
- [ ] TH and EN are complete;
- [ ] realtime stream updates without user refresh;
- [ ] 5-second fallback freshness works during realtime degradation;
- [ ] manual refresh remains available;
- [ ] real lnwjud Watcher API works cross-repo;
- [ ] onboarding is suitable for non-developers;
- [ ] provider setup covers Local, zrok, Cloudflare, Tailscale, ngrok, Custom HTTPS;
- [ ] safe provider automation/helpers exist where feasible on Windows/macOS/Linux;
- [ ] desktop/mobile/Android/iOS layouts are validated;
- [ ] README/docs are user-first and bilingual where appropriate;
- [ ] CI/security/dependency checks pass;
- [ ] dev -> main PR is green and merged;
- [ ] v0.1.0 tag points at the verified main merge SHA;
- [ ] GitHub Release and assets are verified;
- [ ] Native ChatGPT continuation task is made non-runnable;
- [ ] durable goal is terminal completed.

## Explicit non-goals for v0.1.0

- remote command execution;
- approving/rejecting agent operations;
- pause/resume control;
- editing files from Watcher;
- exposing raw prompts or hidden model reasoning;
- storing provider API/auth secrets in Watcher.

These can be considered only in a later protocol version with a separate security design.
